# AMANAH Definition of Done

**Version:** 1.0.0  
**Control date:** 2026-10-03  
**Item:** 66  
**Status:** CONTROLLING QUALITY GATE

A deliverable is not complete because a document exists. It is complete when its target stakeholder can actually use it for the intended purpose, the implementation or controlled artifact exists at the authoritative path, its dependencies and evidence are explicit, and exact-head validation passes.

## Universal completion rule

A deliverable is **DONE TO PROJECT CONTROL** only when all applicable conditions below pass:

1. **Purpose is explicit** — the stakeholder, decision or operational task is named.
2. **Authority boundary is correct** — no software, AI, blockchain, laboratory, QR/NFC, device or partner is given a certification/sovereign/financial authority it does not own.
3. **Source fidelity is preserved** — normative text is source-bound; unavailable authority text is not invented.
4. **Architecture is canonical** — AHTE ⇄ Direct JAKIM API ⇄ JAKIM; China → GCC direct.
5. **Implementation exists where implementation is feasible** — code/schema/UI/API/control exists rather than a disconnected concept document.
6. **Evidence and system of record are identified**.
7. **Failure behaviour is defined** — HOLD/QUARANTINE/exception/escalation/rollback is explicit where applicable.
8. **Security/data boundary is defined**.
9. **External dependencies are not hidden** — they are recorded as SOURCE-LOCKED or OPEN GATE instead of being fabricated or deleting capability.
10. **Cross-consistency passes** — public, technical, legal, commercial and operating materials tell the same controlled story.
11. **Automated or manual validation is recorded** — tests/build/browser/QC appropriate to the artifact.
12. **The artifact is indexed and discoverable**.
13. **Duplicate current controllers are removed or explicitly superseded**.
14. **A serious stakeholder can take the next action without asking what the artifact means or where the supporting evidence is.**

## Definition of Done by deliverable type

| Type | Minimum DoD |
|---|---|
| Application feature | UI/workflow + authorization + data model + validation + audit trail + tests + failure state |
| API / connector | contract + auth pattern + idempotency/retry/error model + environment state + UAT pack + monitoring + rollback + production gate |
| Data model | canonical IDs + ownership + lifecycle + relationships + evidence refs + versioning + access/retention |
| SOP | trigger + owner + inputs + sequence + evidence + exception/escalation + output + audit record |
| Website | controlled copy + corporate identity + responsive/accessibility checks + valid links/provenance + no unsupported claims |
| Corporate profile | institutional narrative + complete ecosystem + authority boundaries + current status classifications + stakeholder usability |
| Infographic / visual | readable hierarchy + canonical topology/corridor + source-safe labels + export-ready master |
| Video / voiceover | controlled script/narrative + media asset or production-ready master + captions/transcript + claim control |
| Legal / MOA | exact scope + responsibilities + authority/data/IP/confidentiality + schedules + execution fields + legal-review status |
| Commercial model | formula/model + explicit assumptions + validated-vs-proposal classification + owner for pricing approval |
| KPI/SLA | metric definition + source + owner + calculation + threshold logic + contractual status |
| Training | curriculum + outcomes + assessment/competence boundary + no statutory-authority overclaim |
| Partner playbook | named role + integration/operating model + questions/evidence + commercial/legal/technical next action |
| Hardware/BOM | exact or RFQ-ready specification + function + interface + deployment context + validation/commissioning gate |
| Authority/normative control | exact authoritative source and version; otherwise DATA NOT AVAILABLE — SOURCE-LOCKED |
| Shipment / transaction | real identities + batch/lot + evidence + custody + authority/destination states; architecture/demo never counts as instantiation |

## External-gate rule

A project-controlled deliverable can be complete while an external activation gate remains open **only if** the complete interface/control/operating package is built and the missing external input is explicitly identified with owner and promotion evidence.

Examples: Direct JAKIM production credentials, laboratory accreditation/API, Sinotrans production site/system credentials, port/customs authorization, GCC importer acceptance, finance/Takaful decision, real Shipment 001 evidence.

## Closure test

If the target stakeholder cannot use the output, if a required implementation is missing, if the output relies on an unsupported external claim, or if exact-head validation fails, the item is **not done**.

**Closure:** Item 66 complete to project control.
